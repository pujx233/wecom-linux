# 当前实现说明

企业微信 5.0.13.6005 / Wine 11.20，2026-11-06，源码候选 5.0.13.6005-4。
审查基线为 `fa9bb79cb609f765c2ae21d92f9ee29b5f79ae04`，本轮改动尚未提交或发布。
累计补丁基于已校验的 Wine 11.20 原始归档，共 64 个文件。
原始源码与净补丁可独立重建，组件指纹见 `../release.json`，验证摘要见 `../validation.json`。

## 窗口布局和合成

主体、标题和阴影共用原生外框。适配器通过
`WINE_X11_FRAME_ATTACHED_CLASSES=PerryShadowWnd;TitleBarWindow` 声明随主体移动的附属层；
成员卡和独立工具弹窗保留绝对坐标与独立排序。

附属层请求先保存在 desired 状态，由 owner 提交时使用同一 Win32 坐标快照统一应用。
局部层更新不再回写桌面已经推进的全局位置，合成等待必要的窗口配置确认。
这修复了快速拖动时标题、阴影与正文错位，以及外框被错误撑大的问题。

跨进程绘制由 XDamage 推进。主体改尺寸时，先更新绘制子窗口，再合成目标尺寸的完整外框缓冲。
缓冲作为原生外框的 resize background，准备期间不复制到仍处于旧布局的外框。
外框需要改尺寸时，X11 resize 使用完整预备背景，缓冲准备后再完成绘制计数并提交几何请求。
有真实原生位置或尺寸变化时，保持旧图像和未完成计数，等布局确认后复制新图像并完成。
装饰边距变化时，即使外框总尺寸不变，也显式提交宽高，避免窗口管理器保留旧正文尺寸。
登记几何等待前，比较 X11 外框的实际位置、尺寸和本次请求掩码。
仅边距或层级变化、原生几何未变时，不等待可能不会到来的 `ConfigureNotify`，并提交已完成的逻辑布局。
该判断不区分窗口管理器，也不依靠超时解除等待。
原生窗口改尺寸时直接取得完整图像，避免在最大化动画中混用新尺寸和旧图像。
首帧映射前开始 XSync 事务；正文首帧尚未上传时，装饰布局的复制不能提前提交完成。
正文上传和最终外框复制完成后提交，绘制重入保持待处理状态。

此前初始化同步计数器要求 WM 声明 `_NET_WM_FRAME_DRAWN`，把基础 XSync 与可选扩展错误地绑在一起。
KWin 6.6.6 不声明这个扩展，却会通过基础计数器在首次映射和缩放时冻结 XWayland 提交。
因此旧实现没有向 KWin 提供握手入口，阴影可以在正文完成前作为黑矩形显示。
现在有 XSync 时公布基础计数器；仅在 WM 支持扩展时公布第二个计数器。
基础请求仍在正文上传、外框复制完成后确认，扩展绘制计数的行为保留。
没有按桌面名称分支，也没有新增延时、隐藏菜单或改变阴影内容。

真实 KDE 菜单补测还发现，`WS_EX_NOACTIVATE` 窗口仍声明 `WM_TAKE_FOCUS`。
KWin 在按下鼠标时请求转移焦点，owner 失焦先关闭菜单，点击命令没有机会执行。
现在按窗口样式更新输入提示和焦点协议，不激活窗口不声明这两种原生焦点入口，
同时保留删除、ping 和已启用的基础同步协议。样式变化时同步更新，应用显式激活仍有效。
独立置顶菜单用例在旧驱动收到零组点击、owner 失焦并隐藏；新驱动收到三组完整点击、owner 保持焦点。
真实企微鼠标点击“另存为”和“打开文件夹”均恢复；没有通过改菜单类型或拦截应用消息处理。

逐窗口合成时，将 bounding shape 转成目标图片上带窗口偏移的裁剪区域。
Render 的源图片裁剪不能排除这些形状外像素；Fedora 的 XWayland 会把其 backing pixmap 中的旧像素带入外框。
复用外框缓冲前先清除上次的目标裁剪，再清空缓冲，防止残留旧图像。
不修改窗口实际形状，也不通过删掉阴影或颜色过滤掩盖残留。

内部借用 CS_OWNDC 后保留应用的 dirty 状态，绘制回调不跨应用调用持有窗口锁。

## 层级与显示变化

同 owner、同 topmost 层的 managed frame 按 Win32 顺序同步，仅提交层级请求。
工具窗口拥有 managed 弹窗时，沿用 Wine 原有的 owner 提升规则，避免不受管理的 owner 盖住其弹窗。
同步保留组内已取得的最高原生位置，普通几何配置不再把刚恢复的主窗压到辅助窗口下面。
原生进入和移动事件按实际 Win32 命中目标处理，旧 foreground 通知不能覆盖当前激活状态。

注册表创建正确传递 REG_OPTION_OPEN_LINK，显示重绑定写入正确的目标；
窗口配置使用当前显示原点，修复拔屏后的裁切和最小化恢复。

## 输入法与应用兼容

候选位置保留 IMM32 请求类型。callbacks 模式下，POINT/FORCE 请求只在输入线程、焦点、
caret HWND 和插入点均对应时使用真实 caret 底边，避免候选框遮住正在输入的文字。
CFS_RECT 桥接中未同时保留独立 ptCurrentPos 的缺口仍在。

GDI 驱动 ABI 为 112，core、X11、打印、Wayland 和两份 IMM32 成套部署。
当前功能使用 X11/XWayland。CEF、邮件 DPI、输入桥、字体及标题栏助手保持配套配置。
PnP 按需查询设备关系并合并待处理通知，Mountmgr 只响应 UDisks2 设备变化。

## DPI 与字体

启动器在空闲 prefix 中同步包内字体和回退表，先于版本注册表写入和客户端启动执行。
自动 DPI 优先使用 X11 标准设置，保留用户手工设置；配置只作用于该 prefix。
迁移标记在成功后原子替换，失败不会把半完成的配置记作成功。

初始化、应用升级和实际启动使用同一中文 locale。Wine 在代码页切换时会重建区域字体链接，
原来的混合 locale 会把 Tahoma 的思源回退覆盖为未安装的 SimSun、Microsoft YaHei 等文件。
这解释了英文桌面下真实文件选择窗口显示方块，而中文环境或不同 locale 的探针正常的差异。
回归使用客户端相同的 locale、11 像素 Tahoma、32/64 位程序，并隐藏宿主字体验证正反例。

原始 X11 窗口像素没有 niri 下那条显示方块的标题栏；合成后多出的 25 像素来自 xwayland-satellite。
其 0.8.2 和 0.8.3 装饰代码只选择一个 Open Sans 字体，缺字时没有回退。
独立补丁按 Fontconfig 排序逐字符查找覆盖字体，支持字体集合索引，按需加载并缓存字体，按画布边界裁剪。
四个中文字符的原版负例、修复正例、英文像素不变及 86 项上游测试通过；已在私有第二个 XWayland 实例验证真实标题。
已撤回试验性的 Wine CaptionFont 修改和 Noto 字体别名，没有在产品中改写窗口标题或隐藏缺字。

## 原生文件接口

上传入口调用 `IFileDialog`，使用选项 `0x1a48` 并注册事件回调。
comdlg32 的 PE 层负责 COM 生命周期、模态 owner 和 Win32 消息泵；Unix 层通过私有 D-Bus 连接调用 FileChooser Portal。
32/64 位共用固定宽度的参数槽，Unix worker 异步等待初始方法回复及选择结果，不阻塞 GUI 的取消。
窗口关闭、WM_QUIT、服务退出及取消均释放请求和连接；初始回复之前到达的信号保留到获得请求路径后处理。
响应按请求路径与服务唯一名称核对，再校验 D-Bus 类型、文件 URI 和选中结果。

多选、当前目录、文件类型和保存扩展名映射到原生结果。保存不得返回只读文件。
Portal 不提供中间导航事件，COM 通知描述提交的目录和选择；确认或目录回调可拒绝并重选。
Win32 自定义控件及没有 Portal 等价语义的选项沿用 Wine 界面。
每次 Show 先清除旧结果，后端切换、取消和重复使用不会返回上一次的文件。
复核补齐了保存状态同步：Portal 返回的新类型通过已有 SetFileTypeIndex 更新当前过滤器，
扩展名复用 Wine 的过滤器解析规则；确认回调拒绝后，下一次请求读取当前文件名和类型。
旧实现在切换到日志类型后仍追加 `.txt`，重开时又回到最初文件名，新增用例均先验证了旧实现失败。

shell32 通过 FileManager1 定位文件，通过 xdg-open 打开目录，使用参数数组和 URI 编码传递路径。
带重命名或桌面语义的 SHOpenFolderAndSelectItems 请求保留 Wine 路径。
32/64 位 Explorer 都接入相同接口；启动器只在 prefix 空闲时更新对应 DLL 和 Explorer，原账号目录保留。
`file` 是 xdg-open 通用桌面路径的 MIME 检测依赖；隔离容器缺少它时，目录打开会失败，现已显式声明依赖。

## KDE 现场与本轮复核

[#2 的最新反馈](https://github.com/pujx233/wecom-linux/issues/2#issuecomment-6649452524)
为 Ubuntu 26.04.1、KDE Plasma 6.6.6、RX 580/Mesa 26.0.8、双屏 1440p、Wayland 两屏 130%。
对方已经使用 -3，仍是打开瞬间黑矩形、随后恢复；切到 Plasma X11 后不闪黑，但另有菜单偶尔出现在桌面左上角。
Wine 改成 96 DPI 没有解决；仅应用进程使用 llvmpipe 也没有解决，未覆盖 KWin 自身的绘制路径。

本轮建立独立的 Ubuntu 26.04.1/KWin 6.6.6/Mesa 26.0.8 环境，两屏均为 2560×1440、130%。
实际合成为 OpenGL/Intel，不能代表现场 RX 580；测试工具的输入和截图权限仅在该隔离会话开放。
构造测试把正文绘制推迟，阴影正常绘制：旧驱动三次显示黑矩形且没有计数器，
新驱动三次保持 owner 背景、基础计数器为 0、KWin 禁止提交；正文完成后计数器为 1，才显示正文。
同时校验实际加载的驱动 inode，不能用文件存在代替运行版本确认。

最终驱动在 GNOME 完成九组几何、同步、首帧、取消重开、附属层和形状裁剪回归，
四组输入、穿透、显式激活和预览层级用例也通过。
前一轮包含基础同步修复的驱动在已登录 niri 完成八轮菜单、三次宽度调整、智能助手及正文/外框像素检查；
此后仅补齐原生焦点声明，原账号已转到 KDE 验证，未将前一轮 niri 记录改记为最终驱动实测。
累计补丁重放后的 12,471 个文件与构建源码一致，64 个补丁文件的范围未扩大。
最终驱动在已登录 KDE 客户端完成 100%/130% 缩放、双屏共 24 次真实图片和会话列表右键菜单，
5,439 个截图采样中未见菜单主体整块不透明黑框，10 次正文与外框像素检查通过。
采样平均 150–228 次/秒，输出为 60 Hz，最大采样间隔约 23 毫秒，不能据此排除所有单帧瞬变。
真实上传入口使用 KDE Portal，浏览中文目录及带空格、引号的文件名后取消，owner 恢复可用，没有发送文件。
图片菜单“打开文件夹”调用 Dolphin 并选中原文件；图片“另存为”仍使用旧式 Wine 对话框，中文正常。
原账号在隔离客户端重启后仍保持登录，实际加载的驱动和 prefix 两种架构的 comdlg32 均核对指纹。

补查窗口几何时发现，隔离 KWin 会话切换缩放后曾留下旧比例的 `_NET_WORKAREA`：
XRandR 为 5120×1440，工作区仍为 3938×1108；原有像素检查不足以证明还原尺寸正确。
用标准输出布局变更让 KWin 重新公布工作区后，双屏各三轮最大化与还原均回到原矩形。
该状态与 KWin 先更新输出/工作区、后更新 XWayland scale 的源码顺序相符，
完整 Plasma 是否存在相同行为仍待核实。未在 Wine 加入比例猜测或坐标补偿，产品不自动修改桌面布局。
构造测试证实的是基础同步缺口，尚不能据此把现场全部表现、尤其 Plasma X11 的定位问题宣布解决。
