本次从公开的 `5.0.13.6005-6`、提交 `fb9f590b4a666efe68533a6fcc29af36cf50ecf4` 开始审查。下方各版本的实机、合成器和文件指纹按当次环境记录。

## 2026-11-21 RC17 聊天与搜索串词

**逻辑失焦与 HIMC。** 聊天和搜索共用 HWND、线程和 HIMC，但使用不同的无窗口 RichEdit。
实际 DuiLib 的 `CRichEditUI::DoEvent` 在失焦时先调用 `OnTxInPlaceActivate`，再检查其
`IsFixRichEditImeContext` 开关。关闭时跳过 `WM_KILLFOCUS`，`TxImmGetContext` 也返回空。
仅改 Wine 原生 HWND 焦点或发送一次组合完成，不能补齐控件自己的输入上下文。

修订使用 DuiLib 正式导出的 `SetFixRichEditImeContext` 启用已有实现。MSFTEDIT 只在
`AppDefaults\WXWork.exe\RichEdit` 的 `DuiLibIMEContext=1` 时接入，其他程序保留原转发。
适配器使用 COM 聚合，保持原生 ITextHost、18 个 ITextServices 方法的参数与 HRESULT，
非自身接口继续交给原生对象。原生 non-delegating IUnknown 持有 inner 对象，
ITextServices 为受其生命周期约束的借用引用，避免引用环。调用方已有 outer 时直接转发。
登录配置会覆盖 DuiLib 的进程开关，因此在服务消息和激活完成时调用同一个公开 setter；
实际控件随后按其原有分支发送失焦和查询 HIMC。没有修改厂商二进制、虚表或按光标位置清词。

**快速输入提交旧词。** 上述分支启用后，搜索不再串入旧词，但快速 `nihao` 失焦曾提交为“你哈”。
对照日志确认 IBus 已发送并显示最新“你好”，Wine 最后收到的 XIM draw 仍是“你哈”。
libX11 在同步 SetICValues/Reset 应答期间设置 `waitCallback`，将预编辑回调放进 IC 队列；
解除等待后没有派发，直到下一次回调到达才处理。最新一次回调会因没有后续输入而永久滞留。

包内私有 libX11 在同步 Set/Get/Reset 的正常返回前，解析完应答并释放临时缓冲后派发队列。
队首先脱链，客户端重入只追加队列；回调栈上的生存标记由 IC 清理函数置为失效，
避免回调销毁 IC 后继续访问对象或重复释放队首。析构同时释放未派发的队尾。
正常即时派发保留无需分配的路径。没有新增扫描全局 IM 列表或全局锁。
驱动通过相对 RUNPATH 载入 Wine 目录的私有库；系统 libX11、Mutter、IBus 未修改。

**验证与范围。** 32/64 位的启用、关闭、缺少 DuiLib 共六项，每项 2,907 次接口与生命周期检查。
私有 Xlib 的真实 IBus 协议用例覆盖 480 个上下文、6,083 次检查；系统旧库复现待派发队列没有被处理。
原生客户端候选在不设 LD_LIBRARY_PATH 的情况下完成六轮快速聊天→搜索，每轮搜索仅“文件”，
原词“你好”保留在聊天。最终 DEB 的完整矩阵及实机结果随候选另行记录。
源码回放核对 Wine 全部 12,476 个文件；Xlib 的 1,704 个文件与固定归档、九项发行版补丁和自有补丁一致。

旧 RC16 与回退 R7 前 IMM32/R6 X11 的对照都复现串词，该证据排除了这两组输入修订为直接原因；
未把它扩展为所有历史版本的结论。早期虚表代理、通用 ITextHost 包装和 Wine 消息队列试验均未入包。
会议首次选屏、动态 DPI、#4 GPU 触发请求及 #5 现场过渡不属于此项修复。

## 2026-11-21 RC16 图片复制与托盘恢复

真实企微复制聊天图片时，OLE 发布者对 `CF_BITMAP` 同时报出 `TYMED_GDI | TYMED_ENHMF`。
旧 `render_format` 优先取增强型图元文件，无法生成位图。修订按剪贴板格式选择 GDI 介质，
读取快照时也遵守相同的介质约定。另一个进程读取 `Ole Private Data` 时，旧实现直接解释本机
`FORMATETC` 指针布局，32/64 位交叉枚举会读错字段，32 位发布、64 位读取还会崩溃。
修订识别两种发布端布局，重建设备数据偏移和本机条目，并读取发布端宽度的对象窗口句柄。
RC6 和 RC15 的独立对照均复现了位图和跨位数枚举错误；候选 36 项用例覆盖延迟渲染、
重复格式、目标设备和发布者 flush 后的读取。真实企微的 640×360 图片已在候选中取得原尺寸位图。

托盘恢复时，企微主窗可能仍是 Win32 前台，但原生焦点已被桌面交给 WeMail 辅助窗口。
旧实现把恢复中的 `WM_TAKE_FOCUS` 丢弃。仅允许该消息通过仍不完整：激活最小化窗口已经
让桌面发起恢复，后续 ShowWindow 又登记一次新的状态序号，桌面第一次确认因此被当成旧回执；
先到的焦点请求还会被旧 IconicState 拒绝。修订把原生激活引起的恢复登记为同一状态事务，
并允许已映射的消息目标使用待确认 NormalState 判断激活资格。其他候选窗口仍使用已确认状态。
私有 X11 用例控制焦点请求先于状态确认到达，RC15 的 Win32 前台正确但原生焦点错误，候选两边一致。
最终 DEB 的完整自动与实机结果随候选单独记录。

聊天编辑器和搜索框共用同一个 HWND、线程和 HIMC。当前日志只见组合位置和字体更新，
没有组合完成/取消、输入上下文切换或可访问性子控件焦点事件；真实串词仍可复现。
这条没有按光标距离、应用名或鼠标点击强行清词，不能计作修复。
此前宿主 Mutter 的覆盖入口、包装脚本与私有库已移出加载路径；当前桌面须在下次注销或重启后换回系统库。

## 2026-11-16 双屏会议和跨进程 DPI

在主屏左侧，Windows 屏幕坐标为负。rc3 的 Wine server 在跨进程换算不同 DPI 的窗口坐标时使用了无符号除法。
双屏 200% 下，独立观察进程读取 96 DPI 窗口得到的横坐标为 44736170，正确值为 -3072。
将仓库已有的有符号换算修复纳入 DEB 的总补丁后，同一个用例返回 -3072，并找到正确的显示器。
主屏在左、在右以及 100%、200% 缩放均已对照。默认的两个 workarea 组分别让 96 DPI 和逐屏感知进程创建窗口，由另一种进程查询。

19:18 的真实快速会议打开在右侧主屏，企微在左屏。随后只读查询同一扇真实企微主窗，逐屏感知进程读到横坐标 -2634；
96 DPI 进程读到 22368303，找不到显示器，指定回退主屏时返回右屏。此前 Win32 记录也出现过发起窗口与会议分屏，会议顶层窗口无 owner。
当时的同屏通过记录取自企微本身就在主屏的场景，尚未覆盖从副屏发起的真实会议。

启动器为会议设置的 `dpiAwareness=0` 保住了逻辑尺寸，也使会议按 96 DPI 绘制。
在 192 DPI 的隔离桌面，随包的会议 Qt 对 962×642 的控件只分配了 962×642 的绘制缓冲。
外部 Win32 观察进程测得客户区为 1924×1284，按同一窗口句柄匹配的 Qt 提交记录为 962×642，像素检查返回 1。
启用原生逐屏绘制的对照中，客户区与最后提交的缓冲都是 1924×1284，像素检查返回 0。该对照验证了随包会议 Qt 的绘制能力。
后续原包与候选的实际入会对照见[快速会议选屏与分数缩放](#2026-11-17-快速会议选屏与分数缩放)。

## 2026-11-16 R8 输入法重连

IBus 重启时还复现了客户端退出。旧进程日志包含 Xlib `_XAllocID` 断言，
随后受控的多线程 Wine 客户端也在重连阶段退出，记录到 6 次跨线程 `XOpenIM` 调用。
这两次退出分别保留证据；没有把受控测试当作旧现场全部调用栈。

Wine 原实现把每个线程的显示连接注册到 Xlib 的输入法实例化回调。
[上游实现](https://github.com/mirror/libX11/blob/master/modules/im/ximcp/imInsClbk.c)
遍历进程级回调链表，事件线程可以调用其他显示连接的回调。
本机日志同样记录了这一行为；线程退出时也没有撤销仍在等待的注册。
由此既可能在其他线程重建输入法，也可能在窗口线程退出后继续访问其数据。

修订复用每个 Wine GUI 线程已有的根窗口属性通知：当 `XIM_SERVERS` 更新时，
由显示连接自己的事件线程调用 `XOpenIM`。不再使用进程级实例化回调，
销毁回调只清理其 `client_data` 中的 XIM 引用。
线程的 `xim_enabled` 状态区分主动关闭 XIM 与等待输入法启动，保留 `UseXIM=No`。
通知匹配实际 X 根窗口，兼容 Wine 虚拟桌面自己的根窗口映射。

## 2026-11-14 PE 缓存分配

双倍桌面缩放下，96 DPI 菜单会请求奇数像素尺寸。实机账号菜单请求主体 280×433、
阴影 328×481，Mutter 将外框分配为 328×482。旧代码在 Win32 尚未消费主体高度 434 的回执时，
就用新主体和旧阴影重新计算布局；消费回执时又清空边距，使固定尺寸提示在 481 与 480 之间反复变化。
日志记录了 54,860 次尺寸提示请求，XSync 完成计数停在奇数，内容虽已画好，合成器仍在等待提交完成。

修复在共用配置入口先消费宿主接受的尺寸，再合并附属布局。宿主引起的尺寸调整保留已分配边距，
直到应用更新附属层；应用主动调整尺寸仍重新计算边距。这里只等待尺寸回执，纯移动保持原来的坐标协议。
产品改动位于 `dlls/winex11.drv/window.c`，沿用宿主回执和现有绘制事务，ABI 保持 112。

新增奇数尺寸的 100%/200% 首帧、取消后重开用例，同时核对 Win32 矩形、可见像素和完成计数。
原驱动在同一夹具中停留在未完成状态，候选通过；原有宿主移动领先、最大化和外框测试继续运行。
原账号 96 DPI 的账号、托盘菜单各反复打开六次，并在打开和取消原生文件窗口后复查，菜单均正常显示。
双屏慢速、快速拖动的录像与几何采样另存 QA18，正式回归结果见验证摘要。

### 升级切换

Wine 的桌面、系统服务和标题栏助手可能在企业微信正常退出后继续驻留。
`wineserver -w` 等待所有进程，因此把“应用仍在运行”和“仅后台驻留”都当成忙碌，会一直推迟升级。

新增 `prefix-state.py` 按用户、Wine 可执行文件身份和 prefix 确认进程：仍有应用客户端就保留会话；
应用均已退出时，结束该 prefix 剩余的 Wine 后台服务，再完成配置和更新。
正常启动及升级沿用同一入口，没有新增多版本缓存，也不在应用运行时终止服务。
文件替换继续使用新 inode，已打开的映射不被截断，账号数据保持原位。

启动器用例覆盖运行中唤回、仅后台驻留、服务错误返回和文件映射不变。
真实 Wine/企业微信夹具使用正常关闭消息退出主程序，确认后台仍在、等待超时，再由新版入口完成下一次升级；
同版本启动、用户数据保留和无 7z 首次启动也在同一组验证。

### 成员卡与预览

原排层逻辑会在其他应用处于前台时继续请求抬高后台窗口。Mutter 会按用户时间拒绝这类请求，
不断补发不能修复层级，还会与宿主的前后台策略争用。现在只同步当前前台 Wine 进程的窗口组，
后台顺序交给窗口管理器；后台鼠标事件也交给宿主实际命中的窗口。
前台继续按 Win32 组内顺序命中，再次激活时恢复层级同步。悬停用例同时核对可见像素、消息接收窗口和焦点。

复测还发现，隐藏原前台窗口后，Win32 前台句柄可能暂时为空。
旧代码把下一次原生激活通知发给空句柄，无法同步焦点。现在在这种情况下通知新的原生目标，
并允许从桌面状态接收激活回执。

排序夹具由私有 Mutter 直接注入目标顺序，并核实注入成功；原来的客户端 raise 请求可能被宿主拒绝，不能据此确认前置条件。
注入时将指针移出窗口，避免真实 EnterNotify 自身改动 Win32 层级；鼠标命中单独测试。
19 个场景检查 owned/unowned 成员卡、预览、后台排层、重新激活、辅助窗口、焦点、像素和几何。
独立后台窗口不要求越过前台应用；重新激活后按当时的 Win32 顺序验收。
没有保留试验性的 owner 搜索扩展或曝光事件修改。

宿主策略可见 [Mutter 的原生排层处理](https://github.com/GNOME/mutter/blob/gnome-50/src/x11/window-x11.c#L3004)。

### 最大化与全屏

这部分存在三个相互关联的状态边界：

- 原逻辑把整个宿主回执处理期间都视为宿主几何变化，应用在 WM_SIZE 回调中主动全屏也会被吞掉。
  core 现在单独传递宿主回执和原始无几何请求的标记，标记在应用 WINDOWPOS 回调之后加入。
  X11 用明确来源分类，替代覆盖应用回调的 `state_locks` 判断。
- 保留 `WS_MAXIMIZE` 的无边框全屏需要同时保存最大化还原状态。原逻辑进入全屏时撤掉原生最大化，
  触发临时还原；连续“最大化→全屏”又可能先发送全屏，使后续最大化请求被宿主拒绝。
  现在分别维护两种状态，并先建立最大化状态，再进入全屏，沿用原生回执推进下一步。
- 默认最大化的 Win32 提议尺寸可能覆盖整屏并带边框，宿主随后按工作区缩小主体。
  若立即用新主体尺寸和旧阴影计算 extents，就会短暂公布过大的右、下边距，让宿主再次放大窗口。
  现在记录最大化操作是否将矩形交给宿主选择；显式应用矩形取回控制，宿主回执保持当前归属。
  最大化回执先交给应用完成布局，再从共用入口提交附属窗口边框；
  应用新发出的明确几何请求仍可继续提交。发布布局时新产生的原生状态请求也先等回执，再配置外框。

可调整尺寸的属性按窗口样式判断，不再因默认最大化提议恰好覆盖显示器而临时丢失。
等待绘制只延后最大化几何的同步；宿主最小化仍可取消待绘制布局，不会卡在宿主已最小化、Wine 状态未变的状态。

回归包括自定义和默认最大化、100%/200% 工作区变化、空操作、阴影与非共享框架控制组、
保留最大化标志的全屏、连续状态请求、宿主 WM_SIZE 中重入全屏，以及等待绘制时的原生最小化与恢复。
默认最大化现已纳入正式判定，要求 Win32、原生主体、阴影及外框一致，并检查过程中没有超出工作区的尺寸跳变。

### 输入法接口复核

此前将“CFS_RECT 未使用独立 ptCurrentPos”判断为缺陷，这个判断不成立。
[微软 COMPOSITIONFORM 文档](https://learn.microsoft.com/en-us/windows/win32/api/imm/ns-imm-compositionform)规定：
CFS_RECT 按 rcArea 定位，POINT/FORCE_POSITION 按 ptCurrentPos 定位。原实现已按模式选择坐标。

将 CFS_RECT 的期望改为 ptCurrentPos 会把正确实现判成失败，甚至引入偏移。
这部分产品改动与不必要的 ABI 变更已全部撤回，GDI ABI 保持 **112**。
保留两个字段取不同坐标的测试，按 rcArea 验收；旧运行库与最终候选都需要通过。
原先错误断言产生的两个失败不作为产品缺陷证据。
本轮继续覆盖 32/64 位、96/192 DPI、DPI unaware、普通与共享框架、混合缩放和 IBus 候选定位。

### 蓝牙名称缓存

名称缓存以 `strdup` 分配字符串，引用归零时原来只释放节点，没有释放字符串。
修复在移出红黑树后释放 `name->str`，引用计数和锁的生命周期不变。
新增用例直接编译实际缓存函数，四线程完成 40,000 个名称的获取、复用、增减引用与回收。
旧源码触发 LeakSanitizer，新源码通过；`winebth.so` 已加入构建和组件清单，避免打包遗漏。

## 旧测试复核

另一次回归保持企微运行，把两屏从 100%/100% 切到 100%/200%。XWayland 坐标密度从 96 变为 192，
Wine 对已打开的会议和新开的会议都继续报告 96，客户区仍为 962×642。在同一个桌面重启隔离客户端后才恢复为 1924×1284。

`win32u/sysparams.c` 从该显示源读取有效 DPI。仅在打开下一场会议时重新枚举显示器，仍会读到相同的旧值。

### 显示器移除与待重绘区域

每个进程收到 RandR 通知后，原有查询路径中的设备消失竞态也被复现。
XRRGetOutputInfo 和 XRRGetCrtcInfo 可能在取得资源快照后收到 BadRROutput 或 BadRRCrtc，
Xlib 默认错误处理会终止客户端。修复沿用 Wine 的错误作用域，只接受本次资源 ID、请求类型对应的设备消失错误；
Xlib 返回 NULL 后使用调用处已有的失败处理。其他 X11 错误继续按原流程报告，没有忽略全部 RandR 错误。

另在应用已请求调整大小、尚未处理 WM_PAINT 时拔除主屏，复现了外框永久停留在旧尺寸。

Wine 的可见区域计算本来就不按桌面边界裁剪顶层窗口。现在待重绘区域沿用同一规则，
普通子窗口的父级裁剪保持原逻辑。没有给客户端增加强制重绘或等待时间。
普通移除、待 resize、待 move、待 repaint、最小化后移除五组均通过，包含绘制计数、update region 与主体/外框几何。

## 2026-11-18 会议 DPI 初始化

## RC8 鼠标消息分发

GNOME 46.2 X11 双屏 200% 下，RC7 的快速拖框有时停在倒数第二个坐标。
跟踪到 Wine 已将坐标为 `(3240,535)` 的 `WM_MOUSEMOVE` 交给客户端。客户端还在翻译这条消息时，
服务器把 `(3260,550)` 合并进同一个队列项。随后客户端按原消息 ID 确认读取，服务器删除了已包含最终坐标的队列项。
`WM_LBUTTONUP` 仍带 `(3260,550)`，应用据以提交的移动坐标仍是 `(3240,535)`，选区从 `401×301` 缩成 `381×286`。

`find_mouse_message` 现在只允许合并尚未交给客户端的队列项。新移动和滚轮消息继续按既有条件合并，
已经交给客户端的消息可由其原 ID 正常确认。补丁保留消息坐标、鼠标按键状态、队列顺序及服务端协议。
双架构 `mouse-queue` 回归分别覆盖待读取的移动和滚轮合并，以及读取期间注入后续移动或滚轮事件。

## 2026-11-21 RC12 原生绘制和 DPI 消息

### #5 原生 GDI 缩放同步

RC8 的 `frame_resize_pending` 只对 `has_surface` 窗口生效，并在切换到直接 GDI 绘制时清除。
直接 GDI 客户端因此绕开已有的“绘制完成后提交布局”协议。受控客户端已绘出新尺寸，
随后仍在处理宿主尺寸回调时，外框继续显示旧像素或黑区。
本次移除这两个排除条件，沿用现有绘制完成和 XDamage 提交路径，没有添加延时、重画循环或内容替换。
相同工具链的 RC8 对照有 31/31 个阻塞期样本不一致，修复后 33/33 个样本一致。
实机复核发现 `GetDC/ReleaseDC` 的直接绘制缺少与 `BeginPaint/EndPaint` 对等的完成通知。
`release_dc()` 现在仅对应用主动释放的无表面 DC 通知完成，排除内部释放、丢弃和已有内存表面。
X11 在没有内存表面时消费这项通知，继续使用既有提交和 XSync 顺序。
测试阻止后续 EndPaint 或 ValidateRect 代为完成提交；缺少 ReleaseDC 通知的库停在旧外框和奇数计数，
修复后的库显示新尺寸蓝色像素并推进到偶数计数。真实企微主窗的单次最大化对照也恢复了外框几何。
外进程直接绘制也没有本地 DIB 表面。释放这类 DC 后，绘制进程先同步 X 连接，
再通过已有的无指针消息通知窗口所属进程；接收端在没有本地未结束绘制时完成原生缩放事务。
独立发送进程的负向对照保持旧绿色像素，修复后显示新蓝色像素，并保留原有跨进程上传顺序。
这只证明该原生 GDI 触发路径已修复；#5 报告者的全部黑边和黑屏现象仍待对应现场验证。
