# 代码审查与架构整理

审查基线为原始 Wine 11.20 / `7298a818b79446bae153b8d5aa27235ab3703bf9`。
范围包括 GitHub 从初始提交到 `4470904` 的六次提交、当前适配器修改和累计 Wine 净补丁。
审查覆盖整理前的 40 个文件；移除实验后净补丁涉及 39 个文件。
初轮实际测试之后又进行一次整体审查，并为审查中发现的共享框架换序遗漏补充了回归。
本文区分源代码结论、独立实验和真实客户端证据，不把所有兼容策略称为上游缺陷修复。

## 归因

代码位于 Wine 源码中，不等于问题来自原始 Wine。
邮件跨进程变化没有进入合成、共享框架换序遗漏、合成缓冲反复分配，以及最长一秒的私有属性轮询，
都属于我们先前适配的缺陷或不合适的 workaround。本轮直接修正这些机制。

普通透明窗口输入、HTTRANSPARENT 查找、foreign DC visual 和光标更新确认属于 Wine 层的语义或生命周期问题。
相关修订有各自回归，但仍是私有分支中的上游修复候选，不代表 Wine 上游已经确认或接收。

CEF/V8 旧实现、邮件 DPI 模式、企微自绘阴影和跨进程输入宿主属于应用及组件的兼容边界。
其中有固定版本源码回补，也有配置或窗口角色适配；不能仅凭 Linux 下的表现断言是腾讯原厂缺陷。
下面单列仍保留的策略与 workaround，避免混入“通用根因修复”的结论。

## 架构边界与优化

`win32u` 负责应用绘图完成语义；`window.c` 负责 Win32 与原生窗口的生命周期、几何、owner 和输入区域；
`frame.c` 负责原生像素变化通知；`xrender.c` 负责按 alpha 合成像素；适配器负责企微自身的窗口角色与启动配置。
通知在窗口自己的 GUI 线程消费，同一批重复请求只排队一次；普通重绘不重新计算全部成员几何。
待处理状态独立于消息是否仍在队列，避免应用在宿主状态同步回调中泵消息时丢失更新。
解锁负责重新排队，迁移和销毁清除两种状态，旧通知不会再次合成已经提交的内容；没有增加轮询定时器。

合成 Pixmap、Picture 和 GC 按框架尺寸复用，resize、visual 重建、owner 迁移及销毁路径释放缓存。
输出复制关闭 GraphicsExpose，避免不需要的事件。每次仍读取当前窗口成员和源 pixmap，避免缓存失效后使用旧 XID。
源窗口在装饰合成后保持原像素的实验已通过，没有据此增加另一层“源/输出窗口”架构。

第二轮审查发现 `window_set_config()` 的共享框架分支丢弃 sibling，普通分支又使用了 sibling 的主体 XID。
现在两种路径先验证同一 owner、可见和相同 topmost 层，再统一解析 WM frame。
共享框架保留纯换序请求，不要求几何变化，也不为不保证产生 ConfigureNotify 的纯换序设置等待序列。
相同用例中，旧版显式请求红窗置顶后仍显示蓝窗；修订后红、蓝往返换序正确。
创建后的初始顺序以稳定后的 Win32 枚举为准，单列于报告，避免把窗口管理器激活行为误作测试预期。

工具窗口的稳定管理策略只在 `WINE_X11_OWNED_FRAME=1` 下启用，关闭该模式保留旧的管理选择。
没有为了某个弹窗名称给 Wine 新增 class 白名单、固定坐标、额外刷新定时器或模拟点击。
保留 Wine 原有模块边界，避免把依赖窗口内部状态的代码机械搬到另一个模块而增加导出接口。

## 构建、复用和验收

净补丁直接适用于原始 Wine 11.20，包含生成的 configure 检查；SDK 增加 libxdamage-dev，安装包依赖 libxdamage1。
官方归档 SHA256、补丁 SHA256、运行时与助手指纹分别记录；干净源码构建与当前实际映射的二进制检查分开。
未编译的 `server/user.h` 有符号 DPI 实验未混入发布补丁或已部署 wineserver。

未登录模板从已校验的公开 R3 包取得，账号、邮件及聊天记录不进入发布包。
打包后逐文件检查字节、权限、链接和 root 所有权，并在独立会话测试新目录首次启动及旧助手升级。
正常启动保留原账号；测试不发送消息或邮件，不进行通话。

真实场景包括主窗口拖动、最大化/还原、图片打开及外露区域拖动、展开历史后切换对话、分享记录正文、邮件切换、人物卡片及头像预览。
录屏时间采用编码完成时间上界，不能当作精确 present 时间；开窗动画与图片准备仍有耗时。
输入未校准、工作区边界限位、输入法浮层遮挡、窗口内容尚未就绪等失败样本保留在本地，并与有效结果分开。

本轮明确搁置截图黑屏。当前 XWayland 桌面 DC 读回为黑色，窗口 DC 可读；尚未实现 Wayland 原生捕获接入。
托盘菜单定位未修复；附件收发、审批、音视频、已读人数以及其他桌面与缩放未全面验收。
因此这是有明确通过场景的预览候选，不是全部功能验收完成的稳定发行。

## 后续 XIM 坐标修订

企业微信聊天输入实测使用 `XIMPreeditCallbacks`，原 Wine 只在 `XIMPreeditPosition` 模式传递位置，
所以输入法采用窗口底部的回退位置。仅恢复传递后，应用提供的 composition 点仍是文字顶边，候选框会遮住文字。
本次使用当前焦点的真实 caret 矩形确定底边，要求相同 root、相同起点且请求区域非空并完全位于 caret 内；
不依赖企微窗口类、固定行高或像素偏移。没有有效 caret 时保留应用请求，不猜测 CEF 的自绘光标。

`win32u` 的另一处原有错误是将输入窗口的逻辑坐标当成 per-monitor 坐标，导致 DPI-unaware 程序在
200% 下漏缩放；现在按输入窗口 DPI 转换。caret 查询使用 caret 所属窗口 DPI，两个结果在 X11 层同属 raw screen 坐标。
新增内部查询枚举追加在末尾，旧编号不变；只配套更新 native core/driver，IMM32 保持原样。

libX11 对单独的 spot 更新可能使用 `XIM_EXT_MOVE`，IBus XIM 服务虽然宣告该扩展但不处理它。
位置更新同时附带不变的 `XNFocusWindow`，使用标准属性更新；窗口真实几何变化后只重发已有 focus 属性，
由 XIM 复用已有 spot 重算屏幕位置。它属于协议兼容处理，不改变焦点、不覆盖应用显式位置，也不新增状态缓存。
代码依据：[libX11 1.8.13](https://www.x.org/releases/individual/lib/libX11-1.8.13.tar.xz)、
[IBus XIM 实现](https://github.com/ibus/ibus/blob/1.5.34-rc2/client/x11/main.c)。

最终构建关闭临时诊断，独立 review 检查了坐标域、窗口锁、属性失败返回和 WOW64 调用。
隔离测试的 PM 192、unaware 192/x86、PM 96/无共享框架三组各 14 项通过，包含大范围 `CFS_RECT`
同起点不被移动的负例。真实 5.0.13.6005 通过输入跟随、换行和两块 200% 屏幕间移动；测试草稿已清理，未发送消息。
私有 100%/200% 双屏另有两轮各 20 项通过，最终用原生 X client 原点和局部物理坐标对照，并核对 client 尺寸。
早期仅以 Win32 屏幕坐标为基准的一轮出现过 1 像素差异，记录已保留；后两轮未复现，取整或异步采样原因尚未确证。
该阶段 IME 候选净补丁从官方 base 重放，全部 41 个文件与构建源码一致；当时尚未重建安装包或更新候选指纹。

边界：现有驱动接口只保留 RECT，无法严格区别微小 `CFS_RECT` 与 point；本次仅按实际 caret 范围收窄处理。
显式 `ImmSetCandidateWindow` 和没有 Win32 caret 的跨进程 CEF 输入不在这次修复的已验收范围。
测试运行方法及后续缩放验证见 [IME 回归说明](tests/ime-position/README.md)。

### 后续构建产物回归

driver 为 `128ed661a0437f9b084a01328cef0b84a3277a0ead29644c9ea4aaf24c2fc3a7`。

## 双屏最大化与恢复修订

本次针对 5.0.13.6005 在笔记本副屏最大化时跳到外接主屏，以及最小化后恢复的相关问题。
仅修改通用 Wine 几何和共享框架实现，保留已验证的输入法修订；没有增加企微窗口类、屏幕编号或固定坐标判断。

| 分类 | 原因与修订 |
| --- | --- |
| 既有共享框架适配 | 绕过配置状态机，把 Win32 临时矩形直接重放到 X11。统一走 `window_set_config()` 的 desired/pending/current 状态和确认流程。 |
| 既有共享框架适配 | 原生 frame 调整后，主体子窗口尺寸及 padding 仍可能过期。按真实主体几何同步；非 NormalState 的阴影不参与框架并集。 |
| Wine Win32 坐标语义 | 自定义最大化位置未从主屏坐标换算到目标屏，应用随后按错误位置重新选屏。统一转换自定义 top-level 位置，子窗口保持原路径。 |
| Wine Win32 恢复语义 | 恢复到最大化前过早清除最小化标志，使选屏可能使用图标位置。计算约束期间保留该标志。 |
| Wine 与 X11 窗口管理器协作 | Iconic→Withdrawn→Normal 重新管理时，Mutter 默认放置会覆盖请求位置。仅在该过渡中保留目标，Normal 确认后提交一次位置并清除状态。 |
| Wine 原生状态同步 | 原生 SC_RESTORE 将最大化矩形写入普通位置。最小化前为最大化的窗口保留普通位置，真正的普通还原继续同步原生几何。 |

自定义位置转换遵循 [Microsoft MINMAXINFO 约定](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-minmaxinfo)：
顶层窗口的最大化位置按主屏表达，窗口管理器负责目标屏换算。默认位置保留原工作区处理；自定义位置使用监视器原点，
避免重复加任务栏边距。已保存的绝对位置先转成回调坐标；应用未修改时原样恢复，避免与默认值碰撞。
这份文档是语义依据，不等于已经在 Windows 实机执行兼容性测试。

X11 的 `restore_position` 在实际配置提交后清除，隐藏、再次最小化、重置和销毁路径能取消它。

## 机器人嵌入与微盘退出后续审查（2026-10-28）

### 已确认的根因与修复边界

微盘退出来自既有共享框架适配的生命周期缺陷。`WM_NCCREATE` 中改变窗口角色时，当前窗口或其他
创建中的 owned 窗口尚未进入桌面 Z-order；旧代码用该枚举迁移 native body，会漏掉这些窗口。
随后销毁旧 frame 会连带销毁未迁移的 body，保存的 XID 失效，`set_initial_wm_hints` 的
XChangeProperty 触发 BadWindow，主进程退出；约 56 ms 后 CEF 因父窗口失效而 FATAL。
这确认了本次微盘复现中主进程退出的故障链，不能通过忽略 X11 错误或绕过 CEF 检查解决；
不能据此断言此前每一次进程更替均为同一原因。

### 绘制回调与锁顺序

### 适配中的锁顺序缺陷

`apply_window_pos` 原来持着 get_win_ptr 获取的 USER 锁调用 update_surface_region；
后者再持一层 USER 锁进入 window_surface_set_shape 和 flush。
新增的首帧/形状提交路径会获取 win_data_mutex，而共享框架几何处理中又有
win_data_mutex→USER 的查询，形成可达的 USER→surface→win_data→USER 锁环。
这是新增适配与原有调用方式组合产生的实现缺陷，不是可以用延时或重试掩盖的问题。

修订先完成 WND 元数据与 DC 失效标记，释放外层 USER 锁，再更新 surface 区域。
helper 在 USER 锁内取得 surface 强引用和 ex_style 快照，释放 WND 后才进入区域和 surface 操作，
所有退出路径释放强引用。区域查询、RTL、shape/clip 组合及 flush 语义保持不变。
生产 helper 的 13 项 API 替身检查通过，包括窗口引用移除后的生命周期负例。
这证明被检查的锁/引用合同，不是此前几秒卡死的双线程栈证据，也不代表整个 Wine 锁图均已验证。
