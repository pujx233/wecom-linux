## 后续修复

### 96 DPI 菜单

双倍桌面缩放下，96 DPI 菜单会请求奇数像素尺寸。实机账号菜单请求主体 280×433、
阴影 328×481，Mutter 将外框分配为 328×482。旧代码在 Win32 尚未消费主体高度 434 的回执时，
就用新主体和旧阴影重新计算布局；消费回执时又清空边距，使固定尺寸提示在 481 与 480 之间反复变化。
日志记录了 54,860 次尺寸提示请求，XSync 完成计数停在奇数，内容虽已画好，合成器仍在等待提交完成。

修复在共用配置入口先消费宿主接受的尺寸，再合并附属布局。宿主引起的尺寸调整保留已分配边距，
直到应用更新附属层；应用主动调整尺寸仍重新计算边距。这里只等待尺寸回执，纯移动保持原来的坐标协议。
产品改动位于 `dlls/winex11.drv/window.c`，沿用宿主回执和现有绘制事务，ABI 保持 112。

新增奇数尺寸的 100%/200% 首帧、取消后重开用例，同时核对 Win32 矩形、可见像素和完成计数。
原驱动在同一夹具中停留在未完成状态，候选通过；原有宿主移动领先、最大化和外框测试继续运行。
原账号 96 DPI 的账号、托盘菜单各反复打开六次，并在打开和取消原生文件窗口后复查，菜单均正常显示。

### 升级切换

Wine 的桌面、系统服务和标题栏助手可能在企业微信正常退出后继续驻留。
`wineserver -w` 等待所有进程，因此把“应用仍在运行”和“仅后台驻留”都当成忙碌，会一直推迟升级。

新增 `prefix-state.py` 按用户、Wine 可执行文件身份和 prefix 确认进程：仍有应用客户端就保留会话；
应用均已退出时，结束该 prefix 剩余的 Wine 后台服务，再完成配置和更新。
正常启动及升级沿用同一入口，没有新增多版本缓存，也不在应用运行时终止服务。
文件替换继续使用新 inode，已打开的映射不被截断，账号数据保持原位。

启动器用例覆盖运行中唤回、仅后台驻留、服务错误返回和文件映射不变。
真实 Wine/企业微信夹具使用正常关闭消息退出主程序，确认后台仍在、等待超时，再由新版入口完成下一次升级；
同版本启动、用户数据保留和无 7z 首次启动也在同一组验证。

### 成员卡与预览

原排层逻辑会在其他应用处于前台时继续请求抬高后台窗口。Mutter 会按用户时间拒绝这类请求，
不断补发不能修复层级，还会与宿主的前后台策略争用。现在只同步当前前台 Wine 进程的窗口组，
后台顺序交给窗口管理器；后台鼠标事件也交给宿主实际命中的窗口。
前台继续按 Win32 组内顺序命中，再次激活时恢复层级同步。悬停用例同时核对可见像素、消息接收窗口和焦点。

复测还发现，隐藏原前台窗口后，Win32 前台句柄可能暂时为空。
旧代码把下一次原生激活通知发给空句柄，无法同步焦点。现在在这种情况下通知新的原生目标，
并允许从桌面状态接收激活回执。

排序夹具由私有 Mutter 直接注入目标顺序，并核实注入成功；原来的客户端 raise 请求可能被宿主拒绝，不能据此确认前置条件。
注入时将指针移出窗口，避免真实 EnterNotify 自身改动 Win32 层级；鼠标命中单独测试。
19 个场景检查 owned/unowned 成员卡、预览、后台排层、重新激活、辅助窗口、焦点、像素和几何。
独立后台窗口不要求越过前台应用；重新激活后按当时的 Win32 顺序验收。
没有保留试验性的 owner 搜索扩展或曝光事件修改。

宿主策略可见 [Mutter 的原生排层处理](https://github.com/GNOME/mutter/blob/gnome-50/src/x11/window-x11.c#L3004)。

### 最大化与全屏

这部分存在三个相互关联的状态边界：

- 原逻辑把整个宿主回执处理期间都视为宿主几何变化，应用在 WM_SIZE 回调中主动全屏也会被吞掉。
  core 现在单独传递宿主回执和原始无几何请求的标记，标记在应用 WINDOWPOS 回调之后加入。
  X11 用明确来源分类，替代覆盖应用回调的 `state_locks` 判断。
- 保留 `WS_MAXIMIZE` 的无边框全屏需要同时保存最大化还原状态。原逻辑进入全屏时撤掉原生最大化，
  触发临时还原；连续“最大化→全屏”又可能先发送全屏，使后续最大化请求被宿主拒绝。
  现在分别维护两种状态，并先建立最大化状态，再进入全屏，沿用原生回执推进下一步。
- 默认最大化的 Win32 提议尺寸可能覆盖整屏并带边框，宿主随后按工作区缩小主体。
  若立即用新主体尺寸和旧阴影计算 extents，就会短暂公布过大的右、下边距，让宿主再次放大窗口。
  现在记录最大化操作是否将矩形交给宿主选择；显式应用矩形取回控制，宿主回执保持当前归属。
  最大化回执先交给应用完成布局，再从共用入口提交附属窗口边框；
  应用新发出的明确几何请求仍可继续提交。发布布局时新产生的原生状态请求也先等回执，再配置外框。

可调整尺寸的属性按窗口样式判断，不再因默认最大化提议恰好覆盖显示器而临时丢失。
等待绘制只延后最大化几何的同步；宿主最小化仍可取消待绘制布局，不会卡在宿主已最小化、Wine 状态未变的状态。

回归包括自定义和默认最大化、100%/200% 工作区变化、空操作、阴影与非共享框架控制组、
保留最大化标志的全屏、连续状态请求、宿主 WM_SIZE 中重入全屏，以及等待绘制时的原生最小化与恢复。
默认最大化现已纳入正式判定，要求 Win32、原生主体、阴影及外框一致，并检查过程中没有超出工作区的尺寸跳变。

### 输入法接口复核

此前将“CFS_RECT 未使用独立 ptCurrentPos”判断为缺陷，这个判断不成立。
[微软 COMPOSITIONFORM 文档](https://learn.microsoft.com/en-us/windows/win32/api/imm/ns-imm-compositionform)规定：
CFS_RECT 按 rcArea 定位，POINT/FORCE_POSITION 按 ptCurrentPos 定位。原实现已按模式选择坐标。

将 CFS_RECT 的期望改为 ptCurrentPos 会把正确实现判成失败，甚至引入偏移。
这部分产品改动与不必要的 ABI 变更已全部撤回，GDI ABI 保持 **112**。
保留两个字段取不同坐标的测试，按 rcArea 验收；旧运行库与最终候选都需要通过。
原先错误断言产生的两个失败不作为产品缺陷证据。
本轮继续覆盖 32/64 位、96/192 DPI、DPI unaware、普通与共享框架、混合缩放和 IBus 候选定位。

### 蓝牙名称缓存

名称缓存以 `strdup` 分配字符串，引用归零时原来只释放节点，没有释放字符串。
修复在移出红黑树后释放 `name->str`，引用计数和锁的生命周期不变。
新增用例直接编译实际缓存函数，四线程完成 40,000 个名称的获取、复用、增减引用与回收。
旧源码触发 LeakSanitizer，新源码通过；`winebth.so` 已加入构建和组件清单，避免打包遗漏。

## 旧测试复核

已回查 10 月 28 日至 30 日的原始回复和 Git 记录。`frame-move-race` 最初用于检查
“Win32 位置尚未消费、原生窗口已经移动”及反向顺序，在当时按样式自动合并弹窗的实现下，
曾复现重复叠加位移。它随 `e060d2b` 提交，属于旧实现的定位实验。

随后实机日志证实，主体取原生位置 T2、阴影和标题取逻辑位置 T1，会把两个布局时点混合。
`6d55fa2` 改成显式声明附属类，并以同一 owner 逻辑快照提交；同次提交引入 `attached-anchor`，
分别验证提交前、提交后、原生领先和独立弹窗。原始回复明确保留旧实验，新测试四项有单独对照记录。

旧实验没有声明附属类，却要求 overlay 与 owner 共用 frame。当前未声明窗口应保持独立，
因此不能直接拿旧断言验收现在的实现。坐标例子也说明两者不同：owner 逻辑位置仍为 `(200,200)`、
原生位置已到 `(500,300)` 时，随 owner 保持 `(-16,-16)` 的层应按逻辑位置请求 `(184,184)`；
旧实验则请求绝对位置 `(484,284)`。仅加类声明会同时改变请求含义。

上轮曾尝试迁移，并补入自动跟随回调。该回调与显式命令都报告 `moved`，现有等待函数不能区分请求，
所以四项通过也不足以证明每个命令均已完成。待确认 resize 实验还观察到请求 600 宽后恢复为 500，
尚未核对宿主接受的几何和回执顺序，不能据此确认产品回归。
迁移草稿、原始结果和修改 diff 已保留在本地 QA 记录；正式夹具恢复原样，未加入上轮 50 组统计。

正式验收采用已迁移的 `attached-anchor` 四项，上轮复核后再次运行通过。
跨线程、待确认 resize 和延迟创建仍值得补测，但新夹具需先明确请求语义、逐命令确认和宿主几何判定。
